Three lifecycle services handle scheduled jobs, auto-generation, and event bridging. `StatusDerivation` is a pure-function utility (`workflow-steps/status-derivation.ts`), not a managed service. None are accessible on the module — they run via `$prepareRuntime()`.

## ReminderEngine

Manages automated expiry and due-date reminders via PubSub schedules and handlers.

### Responsibilities

- Schedules 4 cron jobs via `registerReminderSchedules()`; subscribes handlers via `registerReminderHandlers()`
- Publishes `document_expiring` / `document_due` (expiry wins on same scan), `document_expired` / `document_overdue`, `document_escalated`, `weekly_summary`, `scheduled_job_executed`
- Skips snoozed documents; one notification per document per scan; multi-level escalation via `escalationDays`

### Scheduled Jobs

| Job                                  | Cron        | Purpose                                                           |
| ------------------------------------ | ----------- | ----------------------------------------------------------------- |
| `compliance:daily-expiry-scan`       | `0 8 * * *` | Scans active docs, publishes `document_expiring` / `document_due` |
| `compliance:daily-status-transition` | `0 0 * * *` | Derives `expired` / `overdue`, publishes matching events          |
| `compliance:daily-escalation`        | `0 9 * * *` | Publishes `document_escalated` with `escalationLevel` 1..N        |
| `compliance:weekly-summary`          | `0 9 * * 1` | Publishes `weekly_summary` from cached dashboard summary          |
| `compliance:weekly-summary`          | `0 9 * * 1` | Generates and publishes weekly summary                            |

### Reminder Flow

```text
Daily Expiry Scan (8am)
    ↓
Document has expiryDate within reminderDays window?
    ↓ yes
Publish "compliance:document_expiring" { documentId, daysUntilExpiry, ... }
    ↓
ReminderEngine handler → sends notification via configured channel
    ↓
If past expiry → Daily Status Transition (midnight)
    ↓
Publish "compliance:document_expired"
    ↓
Daily Escalation (9am) checks escalationDays
    ↓
Publish "compliance:document_escalated" { escalationLevel: 1/2/3 }
```

## ObligationGenerator

Listens to obligation schedules and auto-generates compliance documents when they come due.

### Responsibilities

- Registers a handler for the `compliance:obligation-generate` scheduled job
- When triggered, finds active obligations whose next period matches the current date
- Creates a new `document` from the obligation template
- Fills in default values (reminder days, escalation days, assignee, reviewer, jurisdiction)
- Publishes `compliance:document_generated` event

### Auto-Generation Flow

```text
Scheduled Job "compliance:obligation-generate" (6am daily)
    ↓
Find active obligations where autoGenerate = true
    ↓
For each: calculate next period (dueDay, dueMonthOffset, frequency)
    ↓
If period matches current date → create document
    ↓
Copy defaults from obligation (reminderDays, escalationDays, assignee, reviewer)
    ↓
Publish "compliance:document_generated" { documentId, obligationId, sourceModule }
```

## EventBridge

Subscribes to external module events and creates compliance documents in response.

### Responsibilities

- Subscribes to 6 cross-module topics via `registerEventBridgeSubscriptions()`; unsubscribes in `$cleanup()`
- Validates payloads with Valibot; skips invalid messages; dedupes by `{sourceModule, sourceEntityId, documentType}`

| Topic                               | Creates                                                              |
| ----------------------------------- | -------------------------------------------------------------------- |
| `hr:employee_onboarded`             | Background-check + ID-verification docs                              |
| `hr:employee_separated`             | Exit-documents + final-settlement docs                               |
| `fleet:vehicle_registered`          | Semi-annual pollution obligation + certificate                       |
| `organization:branch_created`       | Annual trade-license obligation + trade-license and fire-safety docs |
| `accounting:financial_year_started` | Monthly GST-return obligation                                        |
| `masters:contact_created`           | Insurance-policy doc (insurer contacts on organizations only)        |

### Event Bridge Flow

```text
organization:branch_created { branch: { id, name } }
    ↓
Validate payload → skip if invalid
    ↓
Create annual trade-license obligation (sourceEntityId = branch.id)
    ↓
Create trade-license + fire-safety docs (dedupe by documentType)
```

## StatusDerivation (utility)

Pure functions in `workflow-steps/status-derivation.ts` deriving status from dates, not direct assignment.

### Status Derivation Rules

| Condition                               | Derived Status                |
| --------------------------------------- | ----------------------------- |
| No expiry date and not submitted        | `draft`                       |
| Submitted but not reviewed              | `submitted` or `under_review` |
| Reviewed and approved                   | `verified`                    |
| Reviewed and rejected                   | `rejected`                    |
| Past expiry date                        | `expired`                     |
| Past expiry date + grace period         | `overdue`                     |
| Renewed (new document created from old) | `renewed` (old document)      |
| Manually archived                       | `archived`                    |

<Callout type="info">
  Status is **derived**, not set directly. The `verification_status` column is updated by the
  workflow based on date calculations and lifecycle actions.
</Callout>

<Callout type="info">
  Audit trails are written through the platform's `AuditUnit` (`ctx.audit.write()`), not a
  module-specific audit table.
</Callout>
