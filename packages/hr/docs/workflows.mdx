## AnnouncementWorkflow

Access: `p.hr.announcement`

Manages internal-communications announcements: authoring, audience targeting, scheduling, publishing, pinning, and the delivery snapshot.

### Announcement

```ts
create(input: CreateAnnouncementInput)   // draft, or scheduled when scheduleAt is set
update(id: string, patch: UpdateAnnouncementInput)
delete(id: string)
getById(id: string)                      // + recipientCount
list(filters?: AnnouncementFilters)      // pinned-first, then newest first
publish(id: string)                      // idempotent; materializes recipient snapshot, emits announcement:published
schedule(id: string, scheduledFor: string)
cancelSchedule(id: string)
archive(id: string)
restore(id: string)
pin(id: string)
unpin(id: string)
```

### Delivery Snapshot & Stats

```ts
listRecipients(announcementId: string, filters?: RecipientListFilters)
getStats(announcementId: string)
```

`getStats` returns `{ totalRecipients, deliveredUserCount, employeeOnlyCount, readCount, unreadCount, dismissedCount, acknowledgementCount }` — delivery totals from `hr_announcement_recipient`, read/acknowledgement counts from `comms_notification` rows (`sourceModule: "hr"`, `sourceEntity.type: "announcement"`).

### Business Rules

- Only `draft`/`scheduled` announcements can be edited or deleted; `published` is immutable except pin/archive
- Publish is idempotent — re-publishing a published announcement returns it without re-emitting `announcement:published`
- Scheduling requires `scheduledFor` in the future
- Audiences resolve at publish time and snapshot to `hr_announcement_recipient`; `departments` targeting includes the department subtree
- Strong-ref audiences (`employees`, `groups`, `roles`, `individuals`) validate unknown IDs at create/update; weak refs (`branches`, `departments`, `designations`) are ignored at publish time
- `recipientUserIds` on `announcement:published` are auth user IDs (`hr_user.userId`); employees without an HR user appear in the snapshot only
- The inbox, read receipts, and out-of-band delivery live in `@aspen-os/comms` — hr only produces `announcement:published`

### Position Assignment

```ts

transferAssignment(assignmentId: string, input: TransferAssignmentInput)
```

### Structure Views

```ts

getPositionTree(positionId?: string): Promise<PositionTreeNode[]>
getDirectReports(managerId: string)
getSubordinates(managerId: string, depth?: number)
getPeers(employeeId: string)
getTeam(employeeId: string)
```

### Business Rules

- Position names are unique within a department
- `reportsToPosition` cannot create a cycle (ancestor walk, max depth 10); a position cannot be its own parent
- Assignments cannot exceed the position's `headcount`
- An employee has at most one open-ended assignment per position; `isPrimary` is unique per employee among current assignments
- `delete` and `deactivate` are blocked while the position has active assignments
- Assigning an employee closes a conflicting open-ended assignment to the same position; assigning a primary clears the employee's other current primaries
- `transferAssignment` closes the source assignment and opens one at the target, preserving the primary flag
- Direct reports / subordinates / peers resolve the manager through the position `reportsToPosition` chain, falling back to `employee.reportsTo`

- `deleteEmploymentType`, `deleteDesignation`, `deleteEmployeeGrade`, `deleteHolidayList` are soft deletes (`isActive: false`)
