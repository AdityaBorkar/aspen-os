The platform provides a `Workflow` builder for durable, step-based workflows on the server. Define steps with `WorkflowStep`, then call them via `ctx.step.run()` inside `Workflow.name()`. Runs and steps persist to `workflow_runs` / `workflow_steps`.

## Defining Workflows

Register a workflow with `Workflow.name()` — optionally with Valibot `input` validation — then `handler(input, ctx)`.

```ts
import { Workflow, WorkflowStep } from "@aspen-os/platform/server";
import { object, string } from "valibot";

const MyInput = object({ id: string() });

const myWorkflow = Workflow.name("my-workflow")
  .input(MyInput)
  .handler(async (input, ctx) => {
    const row = await ctx.step.run(fetchStep, { id: input.id });
    const count = await ctx.step.run("count", async () => 42);
    await ctx.step.sleep(5_000);
    return row;
  });

await myWorkflow.run({ id: "123" }, { actorId: "user-1" }); // inside or outside run()
```

`ctx` provides `{ actorId, audit, auth, config, db, log, pubsub, runId, step }`. `RunOptions` overrides ambient context; if omitted, `getContext()` supplies `audit`, `auth`, `db`, `log`, `pubsub`.

## Reusable Steps

Create `WorkflowStep` once, reuse across workflows. Steps handle input validation, retries, and result caching.

```ts
const fetchStep = WorkflowStep.name("fetch")
  .input(object({ id: string() }))
  .handler(async (input, ctx) => {
    return ctx.db.select().from(table).limit(1);
  });

await ctx.step.run(fetchStep, { id: "123" }, { retries: 3 });
```

On retry, a completed step's cached `output` is returned without re-executing the handler.

## Inline Steps

For one-off logic, pass a name and inline function:

```ts
const value = await ctx.step.run("compute", async () => expensiveCalculation(), { retries: 1 });
```

## Retries and Sleeping

```ts
await ctx.step.run("send-notification", async () => ctx.pubsub.publish("notify", data), {
  retries: 3,
});
await ctx.step.sleep(5_000);
```

`retries` is per-step; the engine persists `attempt`, `status`, and `duration_ms` per step. Sleeping uses `node:timers/promises`.

## Persisted State

Workflows and steps are owned by `DatabaseUnit` and written via `WorkflowEngine`:

```ts
// tables owned by DatabaseUnit.getSchemas()
workflowRuns; // { id, workflow_name, status, input, output, error, started_at, completed_at, duration_ms }
workflowSteps; // { id, run_id, step_name, status, attempt, output, error, started_at, completed_at, duration_ms }
```

`WorkflowRunStatus = "running" | "completed" | "failed"`; `WorkflowStepStatus = "pending" | "running" | "completed" | "failed" | "skipped"`.

## Handling Errors

Failures serialize via `serializeError` (depth 5 `cause` chain) into `error` jsonb; the logger receives `attempts` and `stepName`. Validation failures throw `SchemaError` from `@standard-schema/utils` before the handler runs.
