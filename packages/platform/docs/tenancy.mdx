Every tenant's data lives in its own Postgres database (control-plane DB + per-tenant DBs). Isolation is physical — a tenant cannot reach another tenant's data because it is in a different database.

## The Platform Class

```ts
import { TenantPlatform } from "@aspen-os/platform/server";

// Database per tenant: run(tenantId, fn)
const p = TenantPlatform.create(config, [modules]);
```

The config type is fixed:

```ts
// TenantConfig = CommonConfig & { db: TenantDatabaseConfig }
```

The `db` config is the **control-plane** database (auth + platform tables); per-tenant DB configuration is derived from `TenantDatabaseConfig` (`controlDbName`, `tenantDbPrefix`, `tenantDbDefaults`, `connection`).

## `run()` Signatures

```ts
// Control-plane work
await p.run("$global", async () => {
  const { db } = getContext(); // control-plane drizzle instance
});

// Tenant work
await p.run(tenantId, async () => {
  const { db, tenantId } = getContext(); // per-tenant drizzle instance
});
```

The caller resolves the tenant ID (e.g. from the auth session's active organization) and passes it to `run()`. One signature — no overloads. `"$global"` selects the control-plane DB; any other id resolves the tenant DB via `getTenantDb`.

## How It Works

### Stable DB Wrapper

`DatabaseUnit.db` is a getter returning a stable wrapper (a `Proxy`) that resolves the correct per-request drizzle instance via `AsyncLocalStorage` at query time. Workflows keep `this.db = units.db.db` — no workflow code changes.

`run(tenantId, fn)` resolves and connects to the tenant DB (global tenant IDs use the control-plane DB).

### Control-Plane Connection

`DatabaseUnit` always holds a control-plane connection. `AuthUnit` always uses `controlPlaneDb` — auth tables are only on the control-plane DB.

```ts
p.db.controlPlaneDb; // drizzle instance for control-plane queries
p.db.pool; // pg.Pool for the control-plane connection
```

### Per-Tenant Operations

The `DatabaseUnit` provides provisioning helpers:

```ts
p.db.getTenantDb(tenantId); // lazily creates + caches per-tenant pool
p.db.pushSchemasToTenant(tenantId, moduleSchemas);
p.db.provisionTenant(tenantId, config); // create + push schemas → { tenancyMode: "isolated", database, host, ... }
p.db.seedTenantDb(dbConfig, async (db) => {}); // run a seed fn against a tenant DB
```

`TenantPlatform.$prepareInfra()` also calls each module's `$prepareTenant(tenantId)` for every tenant returned by the resolver.

<Callout type="info">
  The `TenantDatabaseConfig.resolver` described in older docs does not exist as a config field. A
  dummy resolver is constructed internally in `TenantPlatform.create()`.
</Callout>

### `tenant_id` Column

Tables (except auth tables) gain a `tenant_id` column:

```ts
tenantId: text("tenant_id")
  .notNull()
  .default(sql`COALESCE(current_setting('app.tenant_id', true), 'default')`);
```

It defaults to `"default"` — redundant but harmless, since isolation is physical.

### PubSub

There is exactly **one** pg-boss — the control-plane boss. `publish`/`subscribe`/`schedule` always target it. A subscribing handler's `ctx.db` is the tenant DB (per-tenant subscription), but the boss itself is shared.

<Callout type="warn">
  There is no `publishControlPlane()` method — with a single boss, `publish()` covers both
  control-plane and tenant topics.
</Callout>

### `$prepareTenant()` Lifecycle

`Module` has an optional `$prepareTenant(tenantId: string): Promise<void>`. The platform calls it for each tenant during `$prepareInfra()`. Modules register per-tenant schedules/subscriptions here.

## CLI

The `aspen` binary loads a platform instance from a config file (export `platform`, `p`, or `pm`):

```bash
aspen db-studio --config=src/aspen/server.ts
aspen db-studio --config=src/aspen/server.ts --port 4983 --host 0.0.0.0
aspen tenants --config=src/aspen/server.ts
```

| Command     | Purpose                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------- |
| `db-studio` | Launch Drizzle Kit Studio against the control-plane DB (`--tenant` targets one isolated tenant DB) |
| `tenants`   | List all tenants (via `db.resolver.list()`)                                                        |
