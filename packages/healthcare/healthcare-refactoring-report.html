1. Executive summary

Recommendation: shrink healthcare from 21 groups to 4 clinical modules, and delete ~6 shadow subsystems by routing them through the platform modules that already own those concerns. Keep every clinical workflow; move only custody of generic capabilities (files, messages, tasks, schedules, masters, reports, compliance evidence, HR).
4 clinical modules
hc-foundation (patients, practitioners, facilities, services, pricelists, encounters, branches/counters) · hc-emr (allopathy, dental, ayush, rehab, psych) · hc-ancillary (pharmacy, diagnostics) · hc-care-ops (appointments, nursing, billing, residents, records-clinical)
8 integrations
comms (messaging), dms (files), calendar (scheduling/recall/reminders), tasks (nursing/order tasks), masters (value sets), compliance (evidence/retention/audit views), hr-* (staff), workspace + future reports (explorer/reports)

The two biggest wins are not clinical at all:

  1. Delete the parallel generic stack. Roughly one third of the module (the operations group at 19 actions, the staff group at 10 actions, plus messaging tables living in db-schemas/records.ts, explorer/report tables in db-schemas/operations.ts, and document handling in records/docs-attach.ts) re-implements what comms, dms, calendar, tasks, masters, compliance, hr-*, and workspace already own per AGENTS.md. That is where the module can get smaller without losing any clinic feature.
  2. Fix internal duplication first. Branch CRUD exists twice (admin/create-branch.ts vs operations/branches-create.ts, both publishing healthcare.branch_created); pricelists exist twice (billing/pricelist-upsert.ts vs pricelists/*); “package” exists in five places (services/define-package.ts, billing/package-sell.ts, ayush/sell-package.ts, dental/implant-milestone.ts, rehab/build-package.ts); boards/queues exist in five places (appointments queue, facilities status-board, nursing board, rehab day-board, diagnostics queue). Unifying each of these inside healthcare is a prerequisite to any extraction.

“Keep functionality similar” means: same workflow names available through a compatibility facade (p.healthcare.* keeps working as deprecated delegates), same healthcare.* topic names during transition (dual-publish where custody moves), same Valibot input shapes re-exported, same branch scoping, same gapless numbering, same audit-per-mutation and encounter-immutability guards.

3. Why it hurts

3.1 One module, three different jobs

The same $name owns (a) clinic registration + EMR, (b) supply-chain and revenue execution (pharmacy PO/GRN, lab ops, invoicing), and (c) generic platform plumbing (messaging outbox, file store, explorer/reports, masters, compliance evidence, HR). The bounded-context map already flags the anomaly: every other domain module has 1–9 workflow groups; healthcare has 21 with 140 tables (.working-docs/BOUNDED_CONTEXTS.md context-map table).

Why this ordering matters: extracting to comms/dms/calendar/tasks/masters/compliance/hr before unifying branches, packages, boards, scheduling, messaging, and consents would freeze five variants of each concept into five new cross-module contracts. Internal unification first; extraction second.

4. Principles & non-negotiables

Do

  • Respect the AGENTS.md single surfaces: dms for files, comms for delivery/inbox, notes for generic notes, calendar for reminders (incl. task reminders via the existing task bridge — no second bridge).
  • One workflow action per file; compose public groups in the module router (existing convention, keep it).
  • Keep Valibot for domain input validation; do not introduce new Zod-based domain validation.
  • Keep one workflow group per bounded concept; move custody, keep clinical guards in healthcare.
  • Preserve branch scoping, gapless numbering, audit-per-mutation, and the encounter-immutability gate verbatim.

Do not

  • Do not recreate drive / notifications / task_reminder parallels (explicitly banned in AGENTS.md).
  • Do not add an overloaded platform run(); tenancy stays class-time (Single/Shared/Isolated).
  • Do not replace Drizzle pushSchema() with migration files; do not add FKs where the design uses soft text references.
  • Do not commit .output/; do not hand-edit the better-auth schema; follow kebab-case filenames and the anti-slop lint rules.
  • Do not change clinical semantics to fit the split (return windows, refill caps, re-admin gates, four-eyes, maker-checker stay).

5. Target shape

 TODAY:  p.healthcare.{ 21 groups }  (one Module, 140 tables, 47 topics)

 TARGET (same behaviour, smaller owners):

  CLINICAL (stay in healthcare family — 4 modules)
  ┌─ hc-foundation ─ patients · practitioners · facilities · services · pricelists · encounters · branches/counters
  ├─ hc-emr ───────── allopathy · dental · ayush · rehab · psych   (shared encounter-gate helper)
  ├─ hc-ancillary ─── pharmacy · diagnostics                        (supply + lab, keep 4-eyes/QC)
  └─ hc-care-ops ──── appointments · nursing(clinical view) · billing · residents(daycare) · records(clinical view)

  GENERIC (move custody to the module that already owns it; healthcare keeps thin clinical wrappers)
  healthcare messaging/timelines/shares ──► comms (message/notification/preference/template/channel)
  clinical files/certs/radio-reports ──────► dms (file/version/share/hold/label) + compliance verification
  recalls + appointment/tele/yoga slots ───► calendar (event/attendee/reminder) via existing bridge pattern
  nursing/order-derived tasks + boards ────► tasks (task/project/status) — nursing keeps vitals/IO/pain/drug view
  value sets / test masters / presets ─────► masters (entity/label/uom)
  explorer + report definitions/runs ──────► workspace (views/search) + future reports module
  compliance evidence + retention/audit ───► compliance (obligation/verification/document/audit)
  staff/roster/attendance/leave/payroll ───► hr-core / hr-attendance / hr-leave (+ shift/position)
  branches (org meaning) ──────────────────► management / masters org-branch; healthcare keeps only subdomain routing row

  COMPAT: p.healthcare.* stays as deprecated facades delegating to the new owners;
          healthcare.* topics dual-published during migration, then owned by the new publisher.
Why four clinical modules and not 21 micro-packages? The five EMR specialties share one invariant (open-encounter gate) and one payload shape; splitting them into five packages would quintuple the encounter-guard contract. The ancillary pair (pharmacy + diagnostics) shares barcode/batch/lot discipline and QC/authorization patterns. Foundation is the registration spine everything references by soft id. Care-ops is the visit-execution spine (schedule → nurse → bill → record). Four is the smallest split that removes the god-module without creating a distributed monolith.

7. What moves into existing platform modules

7.1 comms — all out-of-band delivery + opt-outs + templates

Moves: operations.messaging-send / messaging-retry / messaging-optout, patients.log-communication / share-slip, records.share-print / share-whatsapp, residents.family-summary / send-family-summary / feedback / raise-alert, psych.alert-senior escalation path, appointment/recall notifications. Tables: healthcareMessageLog / healthcareMessageOptout (currently in db-schemas/records.ts) → comms.message + comms.preference; healthcare keeps only the clinical reference (patient/encounter ids in event data). Why: single delivery surface + sweeper outbox already exists; healthcare’s queue-message→audit-notify sequence in operations/messaging-send.ts is a second outbox. Keep similar: same input fields accepted by deprecated wrappers; same opt-out blocking error; healthcare.* events still emitted (then comms.* events additionally).

7.2 dms — all file custody, versions, shares, holds

Moves: records.docs-attach / docs-verify, diagnostics.radio-report-attach, appointments.issue-certificate binaries, dental.consent scans, psych/caregiver consent scans. Pattern: healthcare stores clinical metadata (patient, encounter, type, verified-by) and a dms.file id instead of a raw file_path string; verification workflow stays clinical (four-eyes) but version/hold/share enforcement comes from dms.version/share/hold/public-link. Why: single file surface; retention holds and trash discipline must be shared. Do not create a parallel tag/share/trash model.

7.3 calendar — slots, occupancy, recalls, reminders

Moves: slot computation (appointments.compute-slots, practitioner conflict/next-free-slot, facility overlap), occupancy bookings (appointments, dental chairs, rehab/ayush sittings, counselling/tele), recall rules + recall lists (admin recall-rules, appointments.issue-recall, patients.enrol-recall, psych.recall-list), video/tele scheduling metadata. Pattern: follow the existing tasks→calendar bridge precedent — healthcare publishes intent, calendar owns the event/reminder rows; healthcare keeps clash/consent/encounter guards. Why: single reminder surface (explicit AGENTS.md rule); today there are three recall lists and N slot engines.

7.4 tasks — order-derived work execution

Moves: nursing.tasks-from-orders execution + nursing.board state, encounters.place-order fulfilment tracking, diagnostics.queue worklists, dental.pending-jobs. Pattern: clinical order stays in healthcare; fulfilment becomes a tasks.task (project/status/collaboration/link) with the clinical ids attached; nursing board becomes a read view over tasks filtered by patient/encounter, keeping amber/red clinical triage display. Why: no second task/status/automation engine.

7.5 masters — value sets, catalogues, templates

Moves: operations.masters-upsert/get + seed-presets (healthcareMasterEntry), admin master-versions/templates, diagnostics.test-master-upsert/panel-create catalogue parts, services discount-rule value parts, pharmacy item catalogue parts. Pattern: clinical modules reference masters.entity domains instead of local domain/key/value tables. Why: one shared catalogue surface; local seeding (seed-presets.ts) belongs with the catalogue.

7.6 compliance — evidence, verification, retention, audit views

Moves: operations.compliance-evidence/list (healthcareComplianceEvidence), records.retention-check enforcement, records.registers-append/void/export verification aspects, admin.logs + operations.audit-query (thin views over the platform audit unit), psych involuntary-hook + controlled-Rx attestation, diagnostics QC/authorize attestation. Why: compliance already owns obligation/verification/document/audit/dashboard; healthcare should emit evidence, not own the evidence store.

7.7 hr-core / hr-attendance / hr-leave — the entire staff group

Map: staff.upsert-staff + create-role/delete-role/list-roles/disable-user → hr-core.employee/position/access; staff.roster-plan → hr-attendance.shift; staff.attendance-mark → hr-attendance.attendance (drop the active-only shadow check in favour of HR lifecycle state); staff.leave-request/leave-decide → hr-leave (keep maker-checker); staff.payroll-export → HR payroll hook, same export shape. Keep: practitioners stays clinical; practitioners’ leave blocks read HR leave rather than duplicating it. Evidence of misplacement: staff workflows publish OPERATIONS_EVENTS, not staff events (docs/events.mdx:117).

7.8 workspace (+ future reports) — explorer + report definitions

Moves: operations.explorer-query/grant/export-csv + workflow-steps/explorer-tables.ts allow-list, operations.reports-define/get/list/run + healthcareReportDefinition, billing collection-report/dues-aging/gst-export rendering, diagnostics tat-report rendering. Pattern: healthcare keeps the computations (aging, TAT, dues) as query helpers; the shared surface owns grants, views, CSV export, and report-definition storage. Why: every module needs filtered views; a per-module explorer with its own grant table (healthcareExplorerGrant) fragments access control.

7.9 management — branch meaning

Clarify, don’t merge blindly: healthcare_branch is a subdomain-routing row (subdomain unique), not the org tree. After unifying the two branch CRUDs, keep the routing row in hc-foundation but reference management/masters org-branch for org meaning; document the distinction where the bounded-context language section already warns about it.

9. Cross-cutting concerns you must not break

  • Branch scoping: every clinical table carries branch_id default "main"; workflows scope reads/writes to one branch. Any split must keep the branch filter in every query and keep the default. Do not reinterpret branchId as an org-tree id.
  • Gapless numbering: healthcareCounter + nextHealthcareSeries is transactional and shared (UHID, invoice/receipt/package, sale/return/PO/GRN/transfer, lab/radio, registers). If series leave the module, they must leave together with the same atomicity — never give each new module its own counter table with the same series names.
  • Audit + events per mutation: writers call ctx.audit.write() then ctx.pubsub.publish(); reads publish nothing. Preserve the pairing and the topic names during migration (dual-publish when custody moves). Every produced topic still wants a subscriber (AGENTS.md pub/sub rule).
  • Encounter immutability: sign freezes the visit; post-sign changes go through addenda. All five specialty modules + nursing + diagnostics ordering depend on this. The shared fetch step (workflow-steps/fetch-*.ts, 18 files) is the enforcement point — consolidate, don’t copy.
  • Elevated auth: billing:discount-approve, diagnostics:authorize, psych:override must survive with identical semantics (different-approver, reason-required, audited). ACL resource names should not be renamed until callers migrate.
  • Mixed status representation: shared lifecycles use pgEnums; specialty statuses stay clinic-capitalized text (docs/overview.mdx:76). A split that “normalises” these will silently change guard behaviour — don’t.
  • Soft references: cross-entity links are text ids validated by guards, not FKs. New module boundaries must keep the same guard errors (patients/encounters/services/pricelists resolvers), not replace them with joins.

12. Risks, trade-offs & open questions

  • Distributed guards: encounter-gating, four-eyes, and maker-checker currently run in-process via shared fetch steps. After the split they become cross-module contracts — slower to change, harder to keep atomic. Mitigation: keep the guard helpers in one shared clinical kernel (hc-foundation) that the other three depend on, not in each module.
  • Counter contention: one gapless series serving four modules + HR/masters needs the same transactional guarantees. Do not shard counters per module.
  • Event fan-out: 47 topics is already large; dual-publishing temporarily doubles it. Mitigation: dual-publish only moved topics, with a sunset note per topic in docs/events.mdx.
  • Practitioner vs employee: merging clinical identity into HR identity would leak employment lifecycle (onboarding/separation) into clinical authorship. Keep the soft link; do not merge the tables.
  • Resident scope creep: residents is daycare/long-stay, explicitly not IPD/ADT/OT/insurance (per docs/overview.mdx:7). A split is not permission to add ADT — keep the “no ADT/IPD” boundary in the new module’s docs.
  • Open questions for the team: (1) Should video/tele sessions converge on one session model across appointments + psych tele? (2) Should certificates, discharge summaries, and radio reports share one dms verification flow? (3) When the inventory/reports stubs become real, does pharmacy stock-ledger and the explorer move again? (4) Who owns DEFAULT pricelist seeding — masters seed or billing seed?
