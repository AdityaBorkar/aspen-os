1. Executive summary

healthcare is really four different systems wearing one name: (a) a clinic front-office kernel (patients, practitioners, facilities, appointments, encounters, services/pricelists), (b) a five-specialty EMR (allopathy, dental, ayush, rehab, psych), (c) ancillary clinical operations (pharmacy, diagnostics, nursing, residents), and (d) generic platform capabilities that already have a home elsewhere (staff/HR, masters, compliance, reports/explorer, documents, messaging, reminders).

Recommendation: split into 5 focused healthcare modules + migrate 6 generic capability clusters into their canonical platform modules. Keep every current workflow reachable under a compatibility facade (p.healthcare.* keeps working) until consumers cut over. No behavior change in phase 1 — only moves with re-exports and dual-published events.
Today (1 module)healthcare: 21 groups, 140 tables, 19 ACL resources, 47 events

Module shape

  • Healthcare.create({ tenantCodePrefix: "HC" }) → $name = "healthcare", $dependencies = [], no consumed topics. $prepareInfra() returns auth ACL + tenant schemas + events; $initialize / $prepareRuntime / $cleanup are empty (stateless, no schedules/subscriptions).
  • Tenancy: every clinical table carries branch_id (default "main"); healthcare_branch is a subdomain-routing row (not org structure); healthcare_counter backs gapless human numbers (UHID, invoice, sale, lab order, register serials) via workflow-steps/series.ts.
  • Cross-entity links are soft text references (patient_id, encounter_id) enforced by workflow guards, never FKs. Specialty writers gate on an open same-patient encounter (fetchOpenEncounterStep).
  • Shared helpers in workflows/shared/ (8 files, 555 lines): scheduling/overlap math, package lifecycle, pricelist lifecycle, branch lifecycle, consent-unification across 4 consent stores, psych-booking guards, board-query literals, share-guard.
  • Status is split-brain by design: shared lifecycles use pgEnums; specialty statuses stay capitalized text columns so ported guards keep exact semantics.

3. Why the monolith hurts (specific, observable)

Blast radius & review load

  • One ACL file (19 resources), one event map (47 topics), one schema index (984 lines), one router (643 lines) — every specialty change touches shared files.
  • A pharmacy or billing fix rebuilds/reviews alongside psych masking rules and yoga batches. Reviewers must hold all 21 domains in mind.
  • DB schema index re-exports 140 tables; a table rename ripples through types, schemas, steps, and docs.

Duplicated generic capabilities

  • staff re-implements HR (roster/attendance/leave/payroll/roles) that hr-core / hr-attendance / hr-leave already own.
  • operations re-implements masters KV, compliance evidence, and reporting that masters / compliance / reports own.
  • records re-implements file attach/verify (dms), notes/timeline (notes), and outbound shares (comms).
  • Recalls/reminders and task derivation bypass calendar (sole reminder surface) and tasks (sole task surface).

Latent inconsistencies

  • Two package systems: services.define-package/redeem vs billing.package-sell/redeem/expire sharing only a 54-line helper — different tables, statuses, and events.
  • Four consent stores unified only at read time (consent-lifecycle.ts, 217 lines) — writes can drift.
  • Parallel billing CNDN vs pharmacy CNDN; parallel collection-report vs dues-aging vs GST export with no single revenue ledger owner.

Scale signals

  • Diagnostics (22 files, 363-line schema, 302-line psych-adjacent tables excluded) and records (21 files) are each bigger than many whole platform modules.
  • Nursing has the widest table (323-line schema, 12 tables) and the most safety-critical escalation paths — it deserves its own release cadence.
  • Residents duplicates facility-bed, billing-charge, and comms-summary logic instead of composing them.

4. Splitting principles & hard constraints

Read first: repo rules that constrain any proposal. dms is the single document/file surface (no parallel drive model). comms is the single notification/inbox and out-of-band delivery surface (delivery via the comms.message-sweeper outbox worker — no parallel deliver topics). notes owns notes. calendar owns the single reminder surface, including task reminders (tasks publishes, calendar bridges — no second reminder surface). Valibot for domain input validation. One workflow action per file; public groups composed in the module. PostgreSQL names snake_case, no cross-module FKs, Drizzle push (no migrations).
  1. Keep functionality similar: phase 1 is move-only. Same inputs (Valibot schemas unchanged), same guards (open-encounter gate, four-eyes, maker-checker), same audit writes, same event payloads — only the owning module path changes, with a compat facade.
  2. Bounded contexts over layers: split by clinical ownership (who can safely change it), not by technical layer. Pharmacy, diagnostics, and daycare-care each have distinct owners, lifecycles, and release risk.
  3. Canonical surfaces win: when a generic capability already has an owner (HR, masters, compliance, dms, comms, calendar, tasks, notes), healthcare delegates instead of duplicating. Healthcare keeps only the clinical adapter (e.g. "prescribe → sale" link, not the stock ledger itself).
  4. Encounters stay the clinical root: all specialty writers keep gating on an open same-patient encounter. The gate helper moves to the shared kernel both EMR and care modules depend on.
  5. Branch + counter stay shared: healthcare_branch / healthcare_counter and gapless numbering move to the core kernel; every other module consumes them via a declared dependency, never by copying.
  6. Events versioned, not renamed silently: old healthcare.* topics keep publishing alongside new canonical topics until consumers migrate. ACL splits preserve every current permission; elevated operations (billing:discount-approve, diagnostics:authorize, psych:override) keep their semantics.

8. What stays healthcare-specific (and why)

Stays Why it cannot be genericized
Encounter root + sign-immutability + open-encounter gate The single clinical invariant every specialty, pharmacy Rx, lab order, and nursing task depends on. Generic task/doc modules must not own visit semantics.
Five specialty EMRs (SOAP, FDI charts, NAMASTE/TM2, physio scores, psych masking/scales) Regulated clinical semantics (four-eyes, masking, 24h re-admin gates, early-refill gates) with statutory registers. No platform module models this.

9. Cross-cutting concerns (how to split without breaking)

Auth (ACL): 19 resources → per-module slices

  • Core keeps: patient, practitioner, appointment, encounter, facility, service, billing (+ discount-approve), branch.
  • EMR keeps: allopathy, dental, ayush, rehab, psych (+ override) — psych retains elevated semantics and masked-read enforcement.
  • Pharmacy keeps: pharmacy. Diagnostics keeps: diagnostics (+ authorize). Care keeps: nursing, resident.
  • Deleted: operations, and staff-equivalent resources (moved to hr-*/masters/compliance ACLs). Records resource dissolves with the group (dms/comms/notes/compliance ACLs apply; core keeps a narrow consent/merge permission).

Events: 47 topics → dual-publish, then cut over

  • Keep every healthcare.* topic publishing in phase 1–2 (same HealthcareEntityEvent payload). New modules additionally publish canonical topics (e.g. pharmacy-dispense, diagnostics-authorized) — consumers migrate at leisure.
  • Fix the one mis-attribution found: staff mutations currently publish under operations events; after the move they publish hr events (dual-published during transition).
  • Comms/calendar/tasks-bound actions (shares, recalls, derived tasks) emit their canonical target events at the point of delegation so downstream bridges fire once.

Schemas, steps, types

  • Valibot schemas move with their workflows (one group = one schema file already). The 984-line schemas index splits per module; the 643-line workflow router splits per module with a thin compat router re-exporting everything under p.healthcare.*.
  • Shared steps split by ownership: encounter/patient/practitioner/facility/service fetch steps + series + scheduling/pricelist/branch-consent helpers → core. Psych-booking → emr. Board-query literals → move once into core and import (do not fork per board reader). Package-lifecycle → core (single package model). Share-guard → comms adapter.
  • Status enums: pgEnums move with their owning module; specialty text statuses move with emr/care. The split-brain convention is documented per module so it is not "fixed" inconsistently.
  • DB: tables move logically first (same healthcare_ prefix, same Drizzle push). Physical rename is explicitly out of scope for phase 1 — renames break push assumptions for zero behavior gain.
Do not fork the consent stores. The 217-line consent-unification reader is the most drift-prone file in the module. It moves to core exactly once; emr/care/comms read through it. Writes converge on one consent model in phase 3.

10. Migration phases (functionality similar throughout)

Phase Scope Compatibility
0 — Freeze & facade (days) Freeze new cross-group helpers in healthcare. Add deprecation notes to staff/operations/records groups. Stand up empty sibling packages with re-exports. No behavior change. p.healthcare.* is the only public path.
1 — Extract clean splits (1–2 wks) Move diagnostics (22), pharmacy (16), nursing+residents → care (29) as-is behind the facade. Move shared steps they need into core first. Dual-publish events; dual-register ACL. All existing imports still resolve.
2 — Dissolve generics (2–3 wks) Staff → hr-*; operations masters/compliance/reports/explorer → masters/compliance/reports; records docs → dms, timelines → notes, shares → comms; recalls → calendar; nursing tasks → tasks. Facade delegates (healthcare action calls the canonical action). Old topics still published.
3 — Unify & slim (2–4 wks) Single package model (services+billing); single consent write-model; residents slimmed onto facilities+billing+comms; services+pricelists merged; optional billing → revenue promotion. Facade kept; new canonical paths documented as preferred. Migrate internal callers.
4 — Cut over Flip docs to canonical paths (p.emr.*, p.pharmacy.*, …). Retire facade per-group with a changelog; stop dual-publish after consumer ack. Breaking-change window, one group at a time. Audit log proves parity (every mutation still writes audit + event).
Parity check per phase: (1) workflow count per group unchanged (moved, not dropped); (2) audit-write + event per mutation preserved; (3) elevated guards (discount-approve, four-eyes authorize, psych override) covered by tests before the move; (4) docs events/access-control pages regenerated per module.

11. Risks & what not to do

Risk Mitigation
Over-splitting EMR into 5 micro-modules (allopathy/dental/ayush/rehab/psych each alone) DON'T — they share the encounter gate, consent reads, and package patterns. One emr module with 5 groups preserves the shared pattern; split further only if a specialty gains its own release team.
Forking boards/reminders/tasks instead of consuming calendar/tasks Enforced by repo rule (single reminder/task surfaces). Boards become queries; recalls become calendar reminders; derived work becomes tasks.
Rebuilding delivery (WhatsApp/print) inside healthcare Enforced by repo rule (comms owns delivery via outbox). Healthcare keeps payload + share-guard, never the channel.
Renaming 140 tables or event topics too early Explicitly deferred. Logical move first; physical renames only in phase 4 with a compat alias window.
Losing psych masking or four-eyes/maker-checker in the move Move the guard files with the workflows (psych-booking, authorize, discount-approve) and keep ACL elevation identical; add parity tests before phase 2.
Residents quietly becoming IPD/ADT or insurance/TPA scope Out of scope per module docs (no ADT/IPD beds, no OT, no insurance). Care module stays daycare/long-stay; any ADT ambition is a new module, not scope creep here.
