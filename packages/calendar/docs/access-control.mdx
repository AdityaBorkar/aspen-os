The Calendar module declares its ACL via `defineAcl()`, which the platform merges from the module's `ModuleInfra.auth.acl` and applies to `AuthUnit` during `$prepareInfra()`.

## Resources & Operations

```ts title="src/auth.ts"
import { defineAcl } from "@aspen-os/platform/server";

export const acl = defineAcl({
  calendar: ["create", "read", "update", "delete", "set_default"],
  event: ["cancel", "create", "read", "update", "delete"],
  attendee: ["create", "read", "update", "delete"],
  reminder: ["create", "process", "read", "update", "delete"],
});
```

| Resource   | Operations                                          |
| ---------- | --------------------------------------------------- |
| `calendar` | `create`, `read`, `update`, `delete`, `set_default` |
| `event`    | `cancel`, `create`, `read`, `update`, `delete`      |
| `attendee` | `create`, `read`, `update`, `delete`                |
| `reminder` | `create`, `process`, `read`, `update`, `delete`     |

## Row-Level Enforcement

The ACL declares operations; runtime visibility is enforced in the workflows via `services/access-service.ts`:

| Function                  | Rule                                                                | Applied in                     |
| ------------------------- | ------------------------------------------------------------------- | ------------------------------ |
| `assertCanAccess`         | `access = 'global'` OR `ownerId === actorId`                        | calendar/event/attendee reads  |
| `assertCanMutate`         | `ownerId === actorId` OR tenant admin                               | calendar/event/attendee writes |
| `assertCanAccessReminder` | `userId === actorId` OR (target is an event in a readable calendar) | reminder get/update/delete     |

Events, attendees, and reminders **inherit their calendar's access** — they carry no own access column. The task bridge creates reminders for task recipients directly (recipient-scoped via `userId`).

<Callout type="info">
  The ACL is the *declaration* of operations. Role definitions and permission enforcement are
  application-level concerns — the module exposes the workflows that perform these operations; the
  host app decides who may call them.
</Callout>
