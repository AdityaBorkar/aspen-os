The Calendar module owns two time-domain surfaces for a single organization-wide calendar — events with recurrence and attendees, and the platform's single polymorphic reminder surface (`calendar_reminder`) for `event`, `task`, `compliance_document`, and other targets. Scoping is per item via an **audience**, not per calendar.

## Module

```ts title="src/module.ts"
export class Calendar implements Module {
  static create(config?: CalendarModuleConfig): Calendar;
  readonly $name = "calendar"; // proxy key: p.calendar
  readonly $dependencies: readonly string[] = [];
  readonly $consumes: readonly string[] = [
    "task.due_date_changed",
    "task.deleted",
    "task.status_changed",
    "compliance.document_expiring",
    "compliance.document_due",
    "compliance.document_archived",
    "compliance.document_deleted",
  ];
}
```

`$consumes` is introspection-only, never validated. Set `tasksEnabled: false` or `complianceEnabled: false` to skip the respective bridge.

## Configuration

```ts title="src/types.ts"
type CalendarModuleConfig = {
  complianceEnabled?: boolean; // true — subscribe to compliance.document_* events
  reminderScanCron?: string; // "* * * * *" — pg-boss cron for the reminder scan
  tasksEnabled?: boolean; // true — subscribe to task.* events
};
```

```ts
const calendar = Calendar.create({
  reminderScanCron: "* * * * *",
  tasksEnabled: true,
  complianceEnabled: true,
});
const p = IsolatedTenantPlatform.create(config, [calendar]);
```

## Dependencies

No module dependencies (`$dependencies: []`). Runtime wiring via units:

| Unit     | Purpose                                                    |
| -------- | ---------------------------------------------------------- |
| `db`     | Tenant tables; pg-boss schedules                           |
| `pubsub` | Reminder dispatcher cron + task and compliance bridges     |
| `audit`  | Audit writes via `getContext().audit` in `$prepareRuntime` |

Group-audience resolution reads hr-core-owned tables (`employee_group_member`, `hr_user`) by raw SQL, so the module still runs without hr-core (group audiences simply resolve to nobody).

## Architecture

```mermaid
flowchart TB
  subgraph Runtime[runtime — $prepareRuntime]
    RD[reminder-dispatcher<br/>calendar.reminder-scan<br/>* * * * *]
    TB[task-bridge<br/>task.due_date_changed / deleted / status_changed]
    CB[compliance-bridge<br/>compliance.document_*]
  end

  subgraph TenantDB[tenant database — calendarTables]
    E[calendar_event]
    A[calendar_attendee]
    R[calendar_reminder<br/>polymorphic target_type]
  end

  TB & CB -->|materialize rows| R
  RD -->|scan isSent=false & remindAt <= now| R
  RD -->|resolve audience → per-recipient| DUE[calendar.reminder_due] --> comms[comms event bridge]
  E --> A
  E --> R
```

`$initialize({ db, pubsub })` stores refs; `$prepareRuntime()` registers the reminder-dispatcher and both bridges; `$cleanup()` unregisters all three.

## Key concepts

### Audience scoping

Every event and reminder has `audience_type` (`organization` default / `group` / `user`) and `audience_id` (a group id or user id; `null` for organization). Visibility is computed per query from the actor's employee groups; mutation is creator-or-tenant-admin. There is no calendar access column.

### Recurrence on read

`calendar_event.recurrence` is `{ frequency, interval, count?, until?, byDay? }` validated by `EventRecurrenceSchema`. Occurrences are computed on read by `workflow-steps/recurrence.ts`, never materialized. `count` and `until` are mutually exclusive; `byDay` is weekly-only.

### Single reminder surface

`calendar_reminder` is polymorphic (`target_type` / `target_id` → any module entity). Task due-date reminders (`target_type = task`) are three rows per recipient (`due − 1d`, `due − 1h`, `due`) created by the task bridge, each scoped `audience_type = user`. Compliance document reminders (`target_type = compliance_document`) are `expiryPolicyDays` rows per recipient created by the compliance bridge. At dispatch the reminder's audience is resolved to concrete user ids and one `calendar.reminder_due` is published per recipient. No direct cross-module table reads.

## Relationships

```mermaid
flowchart LR
  E[calendar_event] -->|event_id| A[calendar_attendee]
  E -->|target_type=event| R[calendar_reminder]
  R -. target_type/task<br/>compliance_document/custom .-> EXTERNAL[any module entity]
  R -. audience .-> GROUP[employee group]
  E -. audience .-> GROUP
```

All FKs are soft/logical. `reminder.target_id` is free-form except `custom` allows empty.
