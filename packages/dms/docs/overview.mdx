The DMS module is a records-oriented document management system built on `@aspen-os/platform`. Unlike the Drive module (a free-form filesystem with folders and paths), DMS is **class-first**: every upload lands in a **Triage** stage and becomes an active **Document** only after it is assigned to a **Document Class** whose mandatory fields have been filled.

DMS is also a **superset of `@aspen-os/drive`**: the full Drive feature surface — folders, files, labels, public links, item shares, trash, path/access/archive/search/storage services — is ported into the module under `p.dms.files`, `p.dms.folders`, `p.dms.labels`, `p.dms.publicLinks`, `p.dms.shares`, `p.dms.trash` (and `p.dms.driveSearch`). `@aspen-os/drive` is deprecated; existing Drive data and callers migrate to the DMS item tables (`dms_folder`, `dms_file`, `dms_label`, `dms_item_share`, `dms_public_link`, …).

All binary storage is delegated to the platform's `StorageUnit` under version-bound keys (`dms/{tenant}/{documentId}/v{n}/{name}`); DMS owns the indexing semantics — classes, fields, tags, metadata, versions, views, contacts, sharing, search, retention, and the recycle bin.

## Module

```ts title="src/module.ts"
export class Dms implements Module {
  static create(config?: DmsModuleConfig): Dms;
  readonly $name = "dms"; // proxy key: p.dms
  readonly $dependencies: readonly string[] = [];
}
```

The module declares no platform-module dependencies. It is deliberately independent of `@aspen-os/drive` as a package — but it absorbs Drive's feature surface and `dms_*` tables (`dms_folder`, `dms_file`, …), so Drive itself can be deprecated in favor of DMS.

## Architecture

The module operates against the **tenant** database (all 20 tables are tenant schemas; there are no control-plane tables):

```text
TENANT DATABASE
  dms_document, dms_document_version
  dms_document_class, dms_class_field
  dms_tag, dms_document_tag
  dms_view, dms_pin, dms_share, dms_contact
  dms_legal_hold, dms_setting
  dms_folder, dms_file, dms_file_version
  dms_label, dms_item_label, dms_item_share
  dms_public_link, dms_access_log
```

## Initialization

`$initialize()` receives `db`, `auth`, `pubsub`, and `storage` units, stores `db`/`pubsub`, and binds the `StorageUnit` into the storage bridge (module-level runtime, mirroring Drive):

```ts
$initialize(units: {
  db: DatabaseUnit;
  auth: AuthUnit;
  pubsub: PubSubUnit;
  storage: StorageUnit;
}): void;
```

`$prepareRuntime()` registers three scheduled pg-boss jobs with `ctx.audit` + the running DB:

| Job             | Topic                 | Cron         | Purpose                                                                                |
| --------------- | --------------------- | ------------ | -------------------------------------------------------------------------------------- |
| Expiry scanner  | `dms:expiry-scan`     | `5 0 * * *`  | Promotes active documents past their `expiryDate` to `expired`                         |
| Auto-purge      | `dms:auto-purge`      | `30 3 * * *` | Permanently deletes `deleted`/`expired` documents past retention, skipping legal holds |
| Item auto-purge | `dms:item-auto-purge` | `0 3 * * *`  | Permanently deletes trashed files/folders past `trashRetentionDays` (Drive superset)   |

`$cleanup()` unsubscribes and unschedules all three.

## Config

`DmsModuleConfig` (all optional):

```ts
type DmsModuleConfig = {
  allowedContentTypes?: string[]; // [] = all types allowed
  defaultAutoPurgeEveryHours?: number; // 24
  defaultCompression?: CompressionOption; // { enabled: true, mode: "none" }
  defaultDownloadLinkExpiry?: number; // 3600 (s)
  defaultRetentionDays?: number; // 180
  maxDownloadLinkExpiry?: number; // 604800 (7d)
  maxFileSize?: number; // 5 GB
  maxNestingDepth?: number; // 20 (Drive folders)
  maxVersions?: number; // 10
  trashRetentionDays?: number; // 30 (Drive trash)
};
```

## Infrastructure

`$prepareInfra()` returns:

```ts
$prepareInfra(): ModuleInfra {
  return {
    auth: { acl },                      // document, class, contact, share, view, file, folder, ...
    db: { control_plane_schemas: {}, tenant_schemas: dmsTables }, // 20 tenant tables
    events,                             // dms:* topics
  };
}
```

## Key Invariants

- **Triage gate** — no direct uploads into the active store; classification is the only transition out of Triage (§1).
- **Version-scoped keys** — renames and naming-schema application are metadata-only; no S3 object moves (§2.4).
- **Expiry is a lifecycle state** — the expiry scanner promotes documents to `expired`; restore reactivates (§6.1).
- **Retention is class-based; legal hold overrides** — auto-purge skips held documents; `deletePermanently` rejects them (§6.3).
- **Admin-only destructive authority** — classes, settings, holds, shared views, permanent deletes and `emptyBin` are admin-managed.
