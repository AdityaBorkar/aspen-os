The DMS module is a unified document/files management system built on `@aspen-os/platform`. The class-first records system (triage, classes, versions) and the free-form filesystem (folders, paths) are consolidated onto **one `file` entity**: `dms_file` carries both the folder/path attributes of the filesystem and the class/triage/lifecycle attributes of the records system. `file` is the primary term.

All binary storage is delegated to the platform's `StorageUnit` under version-bound keys (`dms/{tenant}/{fileId}/v{n}/{name}`); DMS owns the indexing semantics — classes, fields, labels, metadata, versions, sharing, search, retention, and the trash. Contacts moved to Masters (`p.masters.contacts`); DMS shares still accept `contact` grantees holding Masters contact ids. Saved file views moved to Masters (`p.masters.filterViews`, domain `dms:file`).

## Module

```ts title="src/module.ts"
export class Dms implements Module {
  static create(config?: DmsModuleConfig): Dms;
  readonly $name = "dms"; // proxy key: p.dms
  readonly $dependencies: readonly string[] = [];
}
```

The module requires the `db`, `pubsub`, and `storage` units via `$initialize()` (unit wiring, not module dependencies). It has no hard module dependencies (`$dependencies = []`), so it composes solo or in any subset.

## Architecture

The module operates against the **tenant** database (all 12 tables are tenant schemas; there are no control-plane tables):

```text
TENANT DATABASE
  dms_file, dms_file_version, dms_folder
  dms_class, dms_class_field
  dms_label, dms_entity_label
  dms_share, dms_public_link
  dms_legal_hold, dms_setting, dms_access_log
```

## Lifecycle

```
upload into folder ──────▶ active ───────────▶ trashed ──── retention/auto-purge ──▶ purged
upload to triage ──▶ triaged ──classify──▶ active           (legal hold blocks purge)
                                     active ──expiry──▶ expired ──▶ trashed  (restore reactivates)
```

- **Upload into a folder** → `active` immediately. **Upload without a folder (staged for classification)** → `triaged`; `classify` validates required class fields, applies the file-naming schema (metadata-only rename), assigns `docNumber`, and sets `active`.
- **Soft delete** (records delete or filesystem trash) → `status = trashed`, `deletedAt`/`deletedBy` set. Restore → `active`.
- **Expiry scanner** promotes past-due files to `expired` (retains class, fields, versions).
- **Purge** (auto-purge or admin `deletePermanently`) removes all version objects and rows, cascading labels, shares, public links, and holds. Legal holds block purge.

## Initialization

`$initialize()` receives the `db`, `pubsub`, and `storage` units, stores `db`/`pubsub`, and binds the `StorageUnit` into the storage bridge (`setDmsStorage`). Audit comes from `getContext()` in `$prepareRuntime()`, not `$initialize()`:

```ts
$initialize(units: Record<string, Unit>): void; // uses db, pubsub, storage
```

`$prepareRuntime()` registers two scheduled pg-boss jobs with `ctx.audit` + the running DB, plus the contact-share bridge subscription:

| Job            | Topic             | Cron         | Purpose                                                                                                                          |
| -------------- | ----------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Expiry scanner | `dms:expiry-scan` | `5 0 * * *`  | Promotes active files past their `expiryDate` to `expired`                                                                       |
| Auto-purge     | `dms:auto-purge`  | `30 3 * * *` | Permanently deletes `trashed`/`expired` files past retention and trashed folders past `trashRetentionDays`, skipping legal holds |

It also subscribes to `masters:contact_removed` (contact-share bridge): removing a Masters contact revokes every DMS share granted to that contact, invalidating contact `shareToken`s immediately.

`$cleanup()` unsubscribes and unschedules all three.

## Config

`DmsModuleConfig` (all optional):

```ts
type DmsModuleConfig = {
  allowedContentTypes?: string[]; // [] = all types allowed
  defaultAutoPurgeEveryHours?: number; // 24
  defaultCompression?: CompressionOption; // { enabled: true, mode: "none" }
  defaultDownloadLinkExpiry?: number; // 3600 (s)
  defaultRetentionDays?: number; // 180
  maxDownloadLinkExpiry?: number; // 604800 (7d)
  maxFileSize?: number; // 5 GB
  maxNestingDepth?: number; // 20 (folders)
  maxVersions?: number; // 10
  trashRetentionDays?: number; // 30 (folder trash)
};
```

```ts
$prepareInfra(): ModuleInfra {

```

## Key Invariants

- **Triage gate** — uploads without a folder are staged in Triage; classification is the only transition out of Triage. Uploads into a folder are active immediately.
- **Version-scoped keys** — storage keys embed `{fileId}/v{n}`, so renames, moves, and naming-schema application are metadata-only; no S3 object moves.
- **Expiry is a lifecycle state** — the expiry scanner promotes files to `expired`; restore reactivates.
- **Retention is class-based; legal hold overrides** — auto-purge skips held files; `deletePermanently` rejects them.
- **Admin-only destructive authority** — classes, settings, holds, and permanent trash deletes are admin-managed.
