The Notes module declares its ACL via `defineAcl()`, which the platform merges from the module's `ModuleInfra.auth.acl` and applies to `AuthUnit` during `$prepareInfra()`.

## Resources & Operations

```ts title="src/auth.ts"
import { defineAcl } from "@aspen-os/platform/server";

export const acl = defineAcl({
  note: ["create", "read", "update", "delete"],
});
```

| Resource | Operations                           |
| -------- | ------------------------------------ |
| `note`   | `create`, `read`, `update`, `delete` |

## Row-Level Enforcement

The ACL declares operations; row-level access is enforced in the workflows via `workflow-steps/access-service.ts`:

| Function          | Rule                                              | Applied in         |
| ----------------- | ------------------------------------------------- | ------------------ |
| `assertCanAccess` | `global` OR `ownerId === actorId` OR tenant admin | `get`, `list`      |
| `assertCanMutate` | `ownerId === actorId` OR tenant admin             | `update`, `delete` |

Tenant admins bypass the `list` access filter and can read any note. Admin checks go through the platform `AuthUnit` user service (`ctx.auth`), not raw SQL, so they work across tenancy modes and surface lookup failures instead of swallowing them.

<Callout type="info">
  The ACL is the *declaration* of operations. Role definitions and permission enforcement are
  application-level concerns — the module exposes the workflows that perform these operations; the
  host app decides who may call them.
</Callout>
