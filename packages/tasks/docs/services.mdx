The Tasks module ships `dependency-graph` helpers under `workflow-steps/` (called with an explicit `db` handle) plus a query-building utility under `utils/filter-engine.ts`. None are exposed as module accessors — workflow code consumes them directly.

## ReportService

Consumed by workflow code via `getContext()`; not exposed as a module accessor.

Aggregates task, assignee, and time data into summary, workload, time, and cumulative flow reports.

```ts
getTaskSummary(projectId: string): Promise<{
  byPriority: Record<string, number>;
  byStatus: Record<string, number>;
  total: number;
}>

getWorkloadReport(projectId: string): Promise<{
  assignedCount: number;
  completedCount: number;
  overdueCount: number;
  userId: string;
}[]>

getTimeReport(projectId: string, dateFrom?: Date, dateTo?: Date): Promise<{
  billable: boolean;
  duration: string | null;
  taskId: string;
  userId: string;
}[]>

getCumulativeFlow(projectId: string, dateFrom: Date, dateTo: Date): Promise<{
  count: number;
  date: string;
  statusId: string;
}[]>
```

- `getTaskSummary` groups by `priority` and `statusId` in a single query, then assembles two count maps.
- `getWorkloadReport` joins `task_assignee` with `task` and uses `SUM(CASE WHEN ...)` for completed and overdue counts.
- `getTimeReport` joins `task_time_entry` with `task` to filter by project, grouping by user, task, and billable flag.
- `getCumulativeFlow` executes raw SQL to bucket tasks by `DATE(created_at)` and `status_id`.

## Task Events

Workflows publish `task:*` events directly via `ctx.pubsub.publish(TASK_EVENTS.*, event)` — there is no bridge layer. Publishing happens in the create/update/delete/assign/unassign/comment/link workflows and the status-change path.

```ts
ctx.pubsub.publish(TASK_EVENTS.CREATED, event);
ctx.pubsub.publish(TASK_EVENTS.UPDATED, event);
ctx.pubsub.publish(TASK_EVENTS.DELETED, event);
ctx.pubsub.publish(TASK_EVENTS.STATUS_CHANGED, event);
ctx.pubsub.publish(TASK_EVENTS.ASSIGNED, event);
ctx.pubsub.publish(TASK_EVENTS.UNASSIGNED, event);
ctx.pubsub.publish(TASK_EVENTS.LINKED, event);
ctx.pubsub.publish(TASK_EVENTS.UNLINKED, event);
ctx.pubsub.publish(TASK_EVENTS.COMMENTED, event);
ctx.pubsub.publish(TASK_EVENTS.DUE_DATE_CHANGED, event);
```

`TASK_EVENTS.DUE_DATE_CHANGED` feeds the `@aspen-os/calendar` task bridge, which materializes/cancels task reminders.

## DependencyGraphService

Used by `LinkWorkflow` for cycle detection and graph algorithms.

```ts
wouldCreateCycle(db, sourceId: string, targetId: string): Promise<boolean>
getDependencies(db, taskId: string): Promise<string[]>
getDependents(db, taskId: string): Promise<string[]>
topologicalSort(db, taskIds: string[]): Promise<string[]>
getCriticalPath(db, projectId: string): Promise<CriticalPathResult>
buildDependencyGraph(db, taskIds: string[]): Promise<TaskDependencyNode[]>
```

- `wouldCreateCycle` performs BFS from `targetId` following `blocks` links, returning `true` if `sourceId` is reachable.
- `topologicalSort` uses Kahn's algorithm (in-degree queue). Throws if a cycle is detected.
- `getCriticalPath` computes the longest path by estimated hours using a topological traversal, returning `{ duration, path }`.
- `buildDependencyGraph` returns nodes with their `dependsOn` arrays for client-side rendering.
- Only `blocks`-type links are considered for graph operations.

## FilterEngine

Lives under `utils/filter-engine.ts`. Used by `TaskWorkflow.list()` to build Drizzle WHERE clauses from `TaskFilters`.

```ts
buildTaskWhereClause(filters: TaskFilters | undefined): SQL | undefined
```

- `buildTaskWhereClause` supports: `projectId`, `statusId`, `typeId`, `priority`, `reporterId`, `parentId` (null = top-level), `isArchived`, `label` (array contains), `search` (ilike on title + description), `assigneeId` (correlated `exists` on `task_assignee`).
