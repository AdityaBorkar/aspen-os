The Tasks module manages projects, tasks, statuses, time tracking, comments, attachments, automation rules, saved views, and dependency graphs.

> Task reminders moved to `@aspen-os/calendar` — they are `calendar_reminder` rows with `targetType = task`, materialized by the calendar task bridge from `task:due_date_changed`. This module no longer owns any reminder surface.

## Module Configuration

```ts
import { Tasks } from "@aspen-os/tasks";

const tasks = Tasks.create({
  enableNotifications: true,
});
```

| `enableNotifications` | `boolean?` | `false` | Configures `task:*` event publishing via the notification bridge |

## Initialization

```ts title="src/index.ts"
$initialize(): void
```

The `$initialize()` method is empty. Workflows are flat imported `Workflow` objects aggregated on the class — they are not instantiated per-call. The notification bridge in `services/` is wired into the create/update/delete/assign/unassign/comment/link workflows and the status-change path, so `task:*` events actually fire.

## Module Structure

```text
packages/tasks/src/
  index.ts              # Tasks class + type re-exports
  types.ts              # Re-exports from schemas/ + domain interfaces
  pubsub.ts             # 10 task events + event maps
  auth.ts               # Empty ACL (defineAcl({}))
  db-schemas/           # 16 tables + 7 enums (6 control + 10 tenant)
  schemas/              # Valibot input/filter schemas (one file per entity)
  workflows/            # One file per action (10 workflow groups)
  workflow-steps/       # Reusable fetch-* steps
  services/             # notification-bridge, dependency-graph, report-service
  utils/                # filter-engine, constants
```

## Accessing Workflows

```ts
p.tasks.projects; // → projects (Workflow group)
p.tasks.tasks; // → tasks
p.tasks.statuses; // → statuses
p.tasks.taskTypes; // → taskTypes
p.tasks.timeEntries; // → timeEntries
p.tasks.comments; // → comments
p.tasks.links; // → links
p.tasks.collaboration; // → collaboration
p.tasks.automations; // → automations
p.tasks.views; // → views
```

## Accessing Services

The `Tasks` module exposes no public service accessors. The internal service modules (`report-service`, `dependency-graph`, `notification-bridge`) and the `filter-engine` utility are consumed directly by workflow code, not surfaced as module properties.

<Callout type="info">
  Workflow accessors are plain module properties — no initialization guard. Workflows are stateless
  `Workflow` objects that use `getContext()` at runtime.
</Callout>
