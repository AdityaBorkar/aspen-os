The Tasks module manages projects, tasks, statuses, time tracking, comments, attachments, reminders, automation rules, saved views, and dependency graphs.

## Module Configuration

```ts
import { Tasks } from "@aspen-os/tasks";

const tasks = Tasks.create({
  enableNotifications: true,
});
```

| `enableNotifications` | `boolean?` | `false` | Configures reminder-based pubsub event publishing |

## Initialization

```ts title="src/index.ts"
$initialize(): void
```

The `$initialize()` method is empty. Workflows are flat imported `Workflow` objects aggregated on the class — they are not instantiated per-call. The `enableNotifications` config key is accepted, and the `NotificationBridge` defined in `services/` is not wired into any workflow.

## Accessing Workflows

```ts
p.tasks.projects       // → projects (Workflow group)
p.tasks.tasks          // → tasks
p.tasks.statuses       // → statuses
p.tasks.taskTypes      // → taskTypes
p.tasks.timeEntries    // → timeEntries
p.tasks.comments       // → comments
p.tasks.links          // → links
p.tasks.collaboration  // → collaboration
p.tasks.reminders      // → reminders
p.tasks.automations    // → automations
p.tasks.views          // → views
```

## Accessing Services

The `Tasks` module exposes no public service accessors. The internal service modules (`report-service`, `dependency-graph`, `notification-bridge`) and the `filter-engine` utility are consumed directly by workflow code, not surfaced as module properties.
<Callout type="info">
  Workflow accessors are plain module properties — no initialization guard. Workflows are stateless `Workflow` objects that use `getContext()` at runtime.
</Callout>
