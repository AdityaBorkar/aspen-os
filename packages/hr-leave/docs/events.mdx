Events are typed via `HrEventMap` in `src/pubsub.ts` — 10 per-group maps (`EmployeeEventMap`, `AttendanceEventMap`, …) intersected into one. 17 topics are emitted by workflows; the rest are declared contracts with no in-repo publisher yet (`—` in Trigger). Two topics are consumed internally for position reconciliation.

<Callout type="warn">
  Pubsub starts lazily: publishing to a topic with no `subscribe()` consumer silently drops the
  message. The host app must subscribe to every emitted topic it cares about.
</Callout>

<Callout type="info">
  `announcement:published` is consumed by `@aspen-os/comms` — one `notification` per
  `recipientUserIds` entry (`sourceModule: "hr"`). `announcement.getStats` reads
  read/acknowledgement counts back from those rows. `recipientUserIds` are auth user IDs; employees
  without an HR user are snapshot-only.
</Callout>

## Consumed (reconciliation subscriptions)

Registered in `$prepareRuntime()` via `registerReconciliation`, unregistered in `$cleanup()`.

| Topic                            | Action                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `lifecycle:separation_completed` | Close the employee's open-ended position assignments at `exitDate`, emit `position:unassigned` per assignment |
| `lifecycle:transfer_approved`    | Close open assignments sitting in `fromDepartment` at `effectiveDate`, emit `position:unassigned`             |

## Usage

```ts title="src/services/reconciliation.ts"
await pubsub.subscribe("lifecycle:separation_completed", async (message) => {
  const { employeeId, separationId } = message.data;
});
```
