The Workspace module is a dependency-free personal-workspace surface built on `@aspen-os/platform`: **drafts**, **dashboards** (with widgets and schedules), and per-user **utilities** (pins, recent, quick search, watches). It stores and serves configuration; rendering, analytics execution, and scheduled delivery are the host application's responsibility. Settings live in `@aspen-os/masters` (`p.masters.settings`).

Filter views (saved filter/sort/group configurations) live in `@aspen-os/masters` (`p.masters.filterViews`); workspace widgets keep an inline `filter` or a `viewId` soft reference to a masters filter view.

## Module

```ts title="src/module.ts"
export class Workspace implements Module {
  static create(config?: WorkspaceModuleConfig): Workspace;
  readonly $name = "workspace"; // proxy key: p.workspace
  readonly $dependencies: readonly string[] = []; // no domain-module deps
}
```

## Access Model

Every data entity carries a user-set `access` enum — `personal` (visible only to `ownerId`) or `global` (org-wide within the tenant). Widgets and schedules inherit their parent dashboard's access. Runtime scoping lives in workflow code via `services/access-service.ts`:

| Helper                     | Rule                                                             |
| -------------------------- | ---------------------------------------------------------------- |
| `assertCanAccess(row, id)` | `access = 'global' OR ownerId = actorId`                         |
| `assertCanMutate(row, id)` | ownership of the row, **or** `user.role = 'admin'` (best-effort) |

`list()`/`get()` filter at SQL level (`global OR owner = actorId`); mutations go through `assertCanMutate`. Pins, recent, and watches are always user-scoped (`userId = actorId`) and carry no access column.

| Getter       | Methods                                                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `drafts`     | `create`, `get`, `update`, `list`, `delete`, `submit`, `approve`, `reject`, `publish`, `reopen`, `trash`, `restore`, `duplicate`, `addComment`, `listComments`, `removeComment` |
| `dashboards` | `create`, `get`, `update`, `list`, `delete`, `duplicate`, `export`, `import`                                                                                                    |
| `widgets`    | `add`, `get`, `list`, `update`, `move`, `refresh`, `remove` (top-level group; workflows live under `dashboard/widget/`)                                                         |
| `schedules`  | `create`, `get`, `update`, `list`, `delete`, `pause`, `resume`, `markRun`                                                                                                       |
| `pins`       | `create`, `delete`, `list` (cross-module item-type registry — workspace entities + dms items pinnable)                                                                          |
| `recent`     | `touch`, `list` (bounded — trimmed to `maxRecentItems` per user)                                                                                                                |
| `search`     | `quick` (access-scoped over drafts, dashboards)                                                                                                                                 |
| `watches`    | `subscribe`, `unsubscribe`, `list` (follow-subscriptions on dashboards — distinct from `PubSubUnit` subscribe)                                                                  |

## Filter Views

Saved filter/sort/group configurations live in `@aspen-os/masters` as `p.masters.filterViews` (table `master_filter_view`), consolidated from the former workspace views, tasks saved views, and DMS file views. `domain` stays free-form text (`<module>:<entity>`), so app-defined domains like `recruiter:candidate` work without a platform change; the built-in domains are `workspace:draft`, `tasks:task`, `dms:file`, `compliance:document`, `hr:employee`, and `notes:note`. Masters is storage-only — hosts read a view's `conditions`/`sort` and query their own tables. Workspace widgets reference a view via the `viewId` soft-FK (or an inline `filter`).

## Initialization

`$initialize()` receives the `db` and `pubsub` units and stores them for `$prepareRuntime()` / `$cleanup()`:

```ts
$initialize(units: { db: DatabaseUnit; pubsub: PubSubUnit }): void;
```

`$prepareRuntime()` runs `registerScheduleRunner()` — it enumerates every **active** schedule row and registers a pg-boss cron per schedule (topic `workspace:schedule:<id>`), plus the module's own delivery handler. `$cleanup()` unregisters all of them.

## Config

```ts
type WorkspaceModuleConfig = {

```

`$prepareInfra()` returns:

```ts
$prepareInfra(): ModuleInfra {
  return {
    auth: { acl },                      // draft, draftComment, dashboard, widget, schedule, …

    events,                             // workspace:* topics
  };
}
```

## Key Invariants

- **Dependency-free** — workspace never creates entities in other modules; `domain` is opaque. Hosts subscribe to `workspace:draft_published` to create target entities and read masters filter views to query their own tables.
- **Approval is optional** — `publish` accepts both `approved` and `draft` states; hosts without a review step skip `submit`/`approve`.
- **Widgets are declarative** — `metric`/`breakdown`/`list` widgets require a `domain` and exactly one of an inline `filter` or a `viewId` soft reference to a masters filter view; `embed` widgets forbid a datasource. The module stores configs and tracks `lastRefreshedAt`/`lastError`; it never computes aggregations.
- **Scheduled delivery is event-driven** — the module only emits `workspace:schedule_due`; rendering and sending are the host's job.
