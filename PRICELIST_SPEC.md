# Pricelist Spec — `@aspen-os/pricelist`

Status: draft · Module: `@aspen-os/pricelist` (`$name = "pricelist"`) · All tables tenant-scope, `pricelist_` prefix
Sources (analyzed):

- https://docs.frappe.io/erpnext/price-lists, `/item-price`
- Item-rate touchpoints: https://docs.frappe.io/erpnext/item (`Standard Selling Rate`, `Item Defaults`), https://docs.frappe.io/erpnext/stock-settings (`Auto insert Price List rate if missing`)
- Implemented contract (source of truth, verified in tree): `@aspen-os/products` (`packages/products/src/` — `module.ts`, `pubsub.ts`, `auth.ts`, `db-schemas/item.ts|item-group.ts|item-uom.ts|item-customer-code.ts|item-supplier-code.ts|item-tax.ts|reorder-rule.ts|setting.ts|enums.ts`, `schemas/item.ts|group.ts|item-uom.ts|setting.ts|reorder-rule.ts|variant.ts`, `workflows/item/*`, `workflows/lookup/*`, `workflows/item-uom/*`, `workflows/setting/*`, `workflows/utils.ts`, `utils/constants.ts`, `docs/*.mdx`), `@aspen-os/masters` UOM/contact topics (`packages/masters/src/pubsub.ts`, `db-schemas/unit-of-measure.ts`). `@aspen-os/inventory` is currently a stub (`src/index.ts` empty) — no batch/stock topics exist yet; any batch reference below is a forward-compat soft-FK label gated by `products.item.has_batch_no`.

## 1. Goals / non-goals

Goals: manage selling and buying prices of products across zones, customers, suppliers, currencies-as-labels, batches, and validity windows — one Item Price row per (`item_id`, price-list, UOM, min-qty, customer/supplier/batch, validity) with deterministic fetch order for sales/purchase transactions.

Non-goals (no tables, workflows, events, or reports for these):

1. Automatic discount/margin engine (pricing rules). Manual `rate` + transaction-level discounts only (matches `ACCOUNTING_SPEC.md` §1.4 exclusion). `products.item.max_discount_percent` is read-only context for callers — pricelist never enforces it.
2. Product master, UOM definitions, warehouses, stock ledger (owned by products/masters/inventory; pricelist stores soft-FK `item_id` + UOM snapshot only). Concretely pricelist must NOT recreate any of: `products_item`, `products_item_group`, `products_brand`, `products_manufacturer`, `products_manufacturer_part`, `products_attribute`, `products_attribute_value`, `products_template_attribute`, `products_barcode`, `products_item_alternative`, `products_item_customer_code`, `products_item_supplier_code`, `products_item_tax`, `products_item_uom`, `products_reorder_rule`, `products_setting`, `master_unit_of_measure`.
3. Multi-currency conversion and exchange-rate management (one tenant base currency; `currency` carried as display label only — matches accounting single-currency non-goal). Note: `products` has no currency field at all, so there is no products-side currency default to inherit.
4. Stock Reports including Item Price Stock report (skipped globally per instruction — no report projections).
5. Invoicing, payment terms, tax computation (owned by accounting; pricelist only supplies the fetched `rate`). Item-tax rows (`products_item_tax`) stay in products; pricelist never copies them.

## 3. Functional scope (ERPNext-parity minus §1 exclusions)

### 3.0 Products-module contract (implemented — pricelist must build on exactly this)

Pricelist is a consumer of `@aspen-os/products` (`$name = "products"`, `$dependencies = ["masters"]`, workflow groups `items`, `groups`, `brands`, `manufacturers`, `attributes`, `variants`, `barcodes`, `alternatives`, `itemUoms`, `reorderRules`, `settings`, `lookups`). The following are implemented facts, not assumptions:

- **Items (`products_item`, `products.item.*`).** Price-relevant columns: `default_price_list: text()` (a _label_, not a FK — matches Price List `name`, not `id`), `default_customer_id?`/`default_supplier_id?` (text soft-FKs), `default_uom: text().notNull()`, `default_purchase_uom?`/`default_sales_uom?` (text), `standard_selling_rate?: numeric`, `last_purchase_rate?: numeric`, `max_discount_percent?: numeric` (read-only context, never enforced here), `minimum_order_qty?: numeric`, `lead_time_days?: integer` (item-level procurement lead time — distinct from pricelist row-level vendor `lead_time_days`), `is_sales_item`/`is_purchase_item`/`is_stock_item` (default true), `is_disabled` + `status: active|disabled|archived`, `has_variants`/`template_item_id`/`variant_key` (immutable after create; template binding unchangeable — `update` throws), `has_batch_no`/`has_expiry_date`/`has_serial_no` (toggle locked once `has_transactions = true`), `warranty_days > 0` requires `hasSerialNo`, `hasExpiryDate` requires `hasBatchNo`, service items (`isStockItem=false`) cannot carry serial/batch flags, `item_code` unique (`assertItemCodeUnique`), naming via `item_naming_by: item_code|naming_series` with group `naming_prefix`/`naming_series` fallback. Update path: `products.item.update` (`{id, patch}`) strips `undefined`, blocks archived-item updates, publishes `products.item_updated` with `{changes, item: {id, itemCode}}`. Delete path: `products.item.delete` throws when `has_transactions` or when variants reference the id as `template_item_id`; cascades to barcodes/UOMs/taxes/customer+supplier codes/manufacturer-parts/reorder-rules/template-attributes/alternatives (both directions). `products.item.mark-transacted` flips `has_transactions`; pricelist fetch-use SHOULD call it (or ensure the caller does) so post-transaction immutability locks engage. `is_disabled`/`status` transitions: `disable` sets both (`is_disabled=true, status="disabled"`, publishes `products.item_disabled {itemId}`), `archive` sets `is_disabled=true, status="archived"` (publishes `products.item_archived {itemId}`; archived rows reject update/disable).
- **Groups (`products_item_group`, `products.group.*`).** Columns include `default_price_list: text()` (label), `default_supplier_id?`, `default_warehouse_id?`, cost-center/expense/income accounts, `parent_id`, `is_group`, `is_disabled`, `weightage`, `show_in_website`. Pricelist group fallback MUST call `products.lookup.resolve-defaults({itemId})`, which returns `{priceList, supplierId, warehouseId, costCenter, expenseAccount, incomeAccount}` with `item.default_* ?? nearest-ancestor-group default` (walks `parent_id` up; warehouse falls back to `products_setting.default_warehouse_id`). Direct group-table reads for defaults are a spec violation. `list-by-group({itemGroupId, includeDescendants=true})` collects descendants via `collectDescendantGroupIds` and filters `is_disabled=false`. `disable` publishes `products.item_group_disabled {itemGroupId}`; create/update publish `products.item_group_created|_updated`.
- **Item UOMs (`products_item_uom`, `products.item-uom.*`).** `{item_id, uom, conversion_factor: numeric notNull (> 0, enforced in handler), must_be_whole_number}` with uniqueness on (`item_id`,`uom`) enforced in handler (`add` throws on duplicate). Pricelist row-`uom` validation: (a) accept `item.default_uom`, `default_purchase_uom`/`default_sales_uom`, or any listed `products_item_uom.uom` for that item; (b) conversion across UOMs uses the row's stored factor snapshot × masters `master_unit_of_measure.conversion_factor` semantics (masters: base units carry `conversion_factor = NULL`, derived units require `> 0`; cross-`category` conversion forbidden — see `masters` `convert.ts`). There is NO `allow UOM with conversion defined` inventory setting anywhere in products settings — the draft's F4 reference to it is removed; unlisted-UOM fetch is a miss, not an error.
- **Party/code/tax auxiliaries (read-only for pricelist).** `products_item_customer_code(item_id, customer_id, ref_code)` unique on all three; `products_item_supplier_code(item_id, supplier_id, supplier_part_no)` unique on all three; `products_item_tax(item_id, tax_category?, tax_template?, tax_rate_override?)`; `products_barcode` (globally unique `barcode`, `add`/`list`/`remove`, events `products.barcode_added|_removed`); `products_item_alternative` two-way links; `products_manufacturer` + `products_manufacturer_part`; attributes/variants (`VARIANT_SYNC_ALLOWLIST` includes `defaultPriceList`, `defaultSupplierId`, `defaultPurchaseUom`, `defaultSalesUom`, `maxDiscountPercent` — template→variant sync only, never a price copy). Pricelist party-specific rows use raw `customer_id`/`supplier_id` soft-FKs (masters entities); they MUST NOT join or duplicate the customer/supplier _code_ tables (those map party part numbers, not prices).
- **Reorder rules (`products_reorder_rule`, `products.reorder-rule.*`).** `{item_id, check_in_group_id, request_for_warehouse_id, reorder_level, reorder_qty, material_request_type: manufacture|purchase|transfer (default purchase), is_disabled}`; `products.lookup.get-reorder-rules({itemId})` returns enabled rows. Pricelist ignores reorder events entirely (no-op guard stays).
- **Settings singleton (`products_setting`, `products.settings.*`).** Implemented columns: `auto_insert_price_if_missing` (default false), `default_stock_uom` (default `"Nos"`), `default_valuation_method: fifo|moving_average`, `item_naming_by: item_code|naming_series`, `default_item_group_id?`, `default_warehouse_id?`, `allow_negative_stock`, `clean_description_html` (default true), `batch_naming_series`, `limit_percent`, `over_deliver_receive_role`, `sample_retention_warehouse_id`, `serial_batch_enabled`, `show_barcode_field`. `get` auto-creates the singleton when missing; `update({patch})` is the SOLE writer. Pricelist reads `auto_insert_price_if_missing` (and `default_stock_uom` as a last-resort UOM hint) and MUST NOT write them; pricelist-local flags (`allow_party_specific?`, `allow_batch_specific?`, `require_validity?`) live in `pricelist_setting`.
- **Lookups tx-eligibility (mandatory fetch pre-checks).** `get-by-code({itemCode})` and `get-by-barcode({barcode})` throw when the item is disabled (`is_disabled` or `status != "active"`) or is a template (`has_variants=true` — "never transacts, use a variant"). Pricelist `getRate` MUST apply the same three checks (by `item_id`) and return a miss/throw identically instead of returning a rate for a disabled/archived/template item. `is_sales_item=false` items never fetch on the selling side; `is_purchase_item=false` never on the buying side.
- **Events (exact names + payloads, `packages/products/src/pubsub.ts`).** Produced: `products.item_created {item: {id, itemCode, itemName}}` (NOTE: no rate/UOM in payload — pricelist seeds from `products.item.get` after receiving it), `products.item_updated {changes, item: {id, itemCode}}`, `products.item_disabled {itemId}`, `products.item_archived {itemId}`, `products.item_group_created|_updated|_disabled`, `products.brand_created|_updated`, `products.variant_created {templateItemId, variant: {id, itemCode, variantKey}}`, `products.variant_template_updated {changes, templateItemId}`, `products.reorder_rule_created|_updated|_disabled`, `products.barcode_added|_removed`. Consumed by products (introspection-only): `masters.unit_of_measure_created|_updated|_retired`, `masters.contact_created|_updated`, `inventory.stock_changed` (products declares it, but inventory is a stub — no such topic is emitted today). There are NO `inventory.batch_created|_expired` topics in the tree — the draft's `$consumes` entry for them is removed and replaced with a `has_batch_no`-gated label (see F7).
- **ACL surface (`packages/products/src/auth.ts`).** Resources: `item` (archive/create/delete/disable/enable/read/update), `group`, `brand`, `manufacturer`, `attribute`, `variant`, `barcode` (create/delete/read), `reorder_rule`, `setting` (read/update). Pricelist §7 ACL mirrors this shape with its own resources.

### 3.1 Price Lists

- **F1 — Price List master.** Fields: `name` (unique, e.g. `Standard Selling`, `Standard Buying`, `Zone-East Selling`), `applicability` (`selling|buying|both`), `currency` (label, defaults to tenant base — products provides no currency, so no inheritance), `country?`/`territory?` (opaque labels), `is_enabled`, `price_not_uom_dependent?` (default false — see F4), `default_customer_id?`/`default_supplier_id?` tagging (soft-FK to masters Entity; auto-selects list on transactions for that party — pricelist-local, distinct from products `item.default_customer_id/default_supplier_id` which resolve per-item via `resolve-defaults`). Rules: disabled lists never fetch and are hidden from transaction pickers; `Standard Selling`/`Standard Buying` seeded on tenant provision (by pricelist itself — products does not seed them) and never hard-deleted; rename safe (rows key by `price_list_id`; note products `default_price_list` stores the _label_, so a pricelist rename MUST backfill matching `products_item.default_price_list` + `products_item_group.default_price_list` labels or document the rename as breaking); applicability narrowing (`both → selling`) blocked while opposite-side party-specific rows exist.
- **F2 — List → transaction wiring.** Sales/purchase documents carry `price_list_id`; on `item_id + uom + qty + party + date` the fetch order is: (0) eligibility gate — reject/miss when the products item is disabled/archived/template, or `is_sales_item=false` on selling / `is_purchase_item=false` on buying; (1) party-and-batch-specific row, (2) party-specific row, (3) batch-specific row, (4) UOM+min-qty-validity row in the selected list, (5) group-default list fallback via `products.lookup.resolve-defaults` (`item.default_price_list` label else nearest ancestor group label — NOT a direct group read), (6) `standard_selling_rate` seed (products `products_item.standard_selling_rate`, read via `products.item.get` after `products.item_created` since the event carries no rate) used only when `auto_insert_price_if_missing` (products-owned flag, read-only here) is on and no row exists. No silent cross-list arbitrage — one list per document.

### 3.2 Item Prices

- **F3 — Item Price core.** Fields: `item_id` (soft-FK to products; MUST exist, be eligible per §3.0 lookups, and honor `default_uom` defaulting), `price_list_id`, `uom` (validated against `item.default_uom`/`default_purchase_uom`/`default_sales_uom`/`products_item_uom` rows; factor snapshot stored at create from `products_item_uom.conversion_factor`), `rate` (`numeric()`, per-row-UOM), `packing_unit?` (qty multiplier per UOM unit; 0/NULL = no-op; supports fractional packs like 1.5 kg), `min_qty?` (threshold for this rate to apply; interacts with products `minimum_order_qty` — row `min_qty` must be `>=` item `minimum_order_qty` when both set, else warn), `customer_id?` (visible only when list `applicability` includes selling), `supplier_id?` (visible only when buying), `batch_no?` (forward-compat soft-FK label — inventory is a stub so no batch table/event validation exists; require `products_item.has_batch_no = true`, never validate against a batch master), `valid_from?` (defaults to creation date) + `valid_upto?`, `lead_time_days?` (row-level vendor differentiation — distinct from `products_item.lead_time_days`; surfaces for buyer choice), `note?`, `is_active` (derived: enabled list + within validity + eligible item). Constraints: one active row per (`price_list_id`, `item_id`, `uom`, `min_qty`, `customer_id`, `supplier_id`, `batch_no`, validity-overlap) — overlapping validity with identical keys rejected in handler (no DB exclusion constraint in v1); `rate ≥ 0`; `customer_id` and `supplier_id` never both set; batch rows require `has_batch_no`; service items (`is_stock_item=false`, priced per time-UOM e.g. `$80 per hour`) supported via masters time-category UOMs (cross-category conversion forbidden per masters `convert.ts`); template items (`has_variants=true`) reject all row creates — price the variant `item_id` instead; `max_discount_percent` from products is exposed to callers alongside the rate, never enforced here.
- **F4 — UOM handling.** Default UOM-dependent: transaction in a different UOM converts via the stored `products_item_uom.conversion_factor` snapshot (`rate × factor`) only when `price_not_uom_dependent=true` on the list AND masters allows the conversion (same `category`; base units have `conversion_factor=NULL`, derived require `>0`); otherwise only exact-UOM rows fetch (e.g. Tomatoes `per Kilo` never auto-fills a `per Box` line). `must_be_whole_number` (products item-UOM) is enforced on the transaction qty at fetch time (fractional qty → miss, not error). There is no products/inventory "allow UOM with conversion" setting — that draft claim is withdrawn.
- **F5 — Auto-insert on first transaction.** When `auto_insert_price_if_missing` (sole writer: `products.settings.update`; pricelist reads via `products.settings.get`, default false) is on and a sales/purchase transaction carries a manual `rate` with no matching Item Price, pricelist auto-creates the missing row in the document's list (rate = transaction rate, UOM = transaction UOM, `valid_from` = transaction date) AND calls `products.item.mark-transacted` semantics (directly or via caller) so `has_transactions` locks engage. When off, the `standard_selling_rate` value (read via `products.item.get`, since `products.item_created` carries only `{id, itemCode, itemName}`) seeds the initial Item Price at item-create time only; later manual rates stay document-local. Auto-insert never overwrites existing rows and never fires for party/batch-specific prices (those require explicit creation). Auto-insert also updates `products_item.last_purchase_rate` on the buying side only through `products.item.update` (pricelist never writes the column directly; `last_purchase_rate` writer stays products).
- **F6 — Validity + lead-time differentiation.** Multiple rows per (`item_id`, list, UOM) coexist with non-overlapping validity windows (seasonal/limited offers) or distinct `lead_time_days` (same product, faster vs slower vendor — row-level, not `products_item.lead_time_days`). Fetch filters `valid_from ≤ txn_date ≤ valid_upto ?? ∞` and surfaces `lead_time_days` for buyer choice; expired rows retained for audit, excluded from fetch.
- **F7 — Party/batch-specific pricing.** Optional `customer_id` (selling lists) or `supplier_id` (buying lists) pins a rate to one party — soft-FK to masters entities, independent of products `item-customer-code`/`item-supplier-code` ref-code tables; optional `batch_no` pins to one batch label (e.g. premium lot) gated on `products_item.has_batch_no=true` (and `has_expiry_date` interplay respected: expiry-tracked items SHOULD carry batch prices, never generic-only). No `inventory.batch_*` events exist (inventory stub), so batch eligibility is derive-from-products-only. Specificity wins over generic rows (see F2 order). Bulk-assign via `assign_to_parties` action (one rate template × N parties creates N rows — explicit rows, never dynamic rules).

### 3.3 Settings owned here

- **F8 — Owned settings.** Pricelist READS (never writes) the products singleton via `products.settings.get`: `auto_insert_price_if_missing` (execution flag), `default_stock_uom` (default `"Nos"` — last-resort UOM hint when an item has no `default_uom`-family value and no `products_item_uom` rows). `default_selling_list_id?`/`default_buying_list_id?` are pricelist-local (products has no list ids — its `default_price_list` is a text label; the mapping label↔id lives here). Pricelist-local (in `pricelist_setting` singleton, same get-auto-creates + `update({patch})` pattern as products): `allow_party_specific?` (default true), `allow_batch_specific?` (default true), `require_validity?` (default false). Everything else by reference: items/groups/UOM-links/codes/taxes/reorder-rules (products), UOM definitions (masters `master_unit_of_measure`), batches (inventory stub — labels only), parties (masters entities/contacts).

## 4. Document lifecycles + fetch semantics

| Entity                                | Draft → …                                                                                                                                                                                                                                  | Effect                                                                                                                                                                                                                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Price List                            | `enabled ↔ disabled`; delete only when zero Item Prices                                                                                                                                                                                    | Disabled hides from pickers + blocks fetch; seeded standards never deleted                                                                                                                                                                                                                  |
| Item Price                            | `active → expired → (superseded)`; `cancelled` only before first fetch-use; never hard-delete used rows (mirrors products `delete` guard: `has_transactions` blocks delete — disable/archive instead)                                      | Expiry is time-driven (`valid_upto` pass) or explicit `expire` action; history retained for audit                                                                                                                                                                                           |
| Item (products-owned, read-only here) | `active → disabled → archived` (`disable` sets `is_disabled=true, status="disabled"`; `archive` sets `is_disabled=true, status="archived"`; archived rejects update/disable; `has_transactions` locks UOM/batch/variant/valuation toggles) | Pricelist fetch honors the same gates; pricelist rows for a disabled/archived item stop fetching but are retained; `products.item.delete` does NOT cascade to pricelist rows (no FKs) — pricelist MUST expose `hasPriceReferences(itemId)` so host can block item delete while prices exist |
| Fetch                                 | Stateless read (`getRate(item_id, price_list_id, uom, qty, party_id?, batch_no?, txn_date)`) with products eligibility pre-check (`status/is_disabled/has_variants/is_sales_item/is_purchase_item`)                                        | Returns single `rate + source_row_id` or miss (caller falls back per F2); no writes except auto-insert path (which also drives `mark-transacted` semantics)                                                                                                                                 |

Invariants: one list per document; fetch is deterministic (eligibility → specificity → validity → min-qty → lead-time); expired/disabled/ineligible never fetch; overlapping-validity duplicates rejected; auto-insert creates only generic rows; `rate` snapshots into documents (later price edits never rewrite posted vouchers); products `default_price_list` labels must resolve to an existing enabled list name at fetch time (dangling labels → miss, not error).

## 5. Domain events (`pricelist.*`)

Produced (type-level contract; platform has no runtime side effects): `pricelist.price_list_created|_updated|_disabled`, `pricelist.item_price_created|_updated|_expired` (consumed by inventory for `basic_rate` snapshots and by accounting for order/invoice rate defaults; products consumes to refresh `last_purchase_rate` cache — via `products.item.update`, never a direct column write).
Consumed (`$consumes`, introspection-only — exact implemented topics only): `products.item_created|_updated|_disabled|_archived` (seed/auto-insert triggers, UOM/default validation; `item_created` payload is `{item: {id, itemCode, itemName}}` so rate/UOM seeding requires a follow-up `products.item.get`), `products.item_group_created|_updated|_disabled` (group-default chain invalidation), `products.variant_created|_template_updated` (variant rows priced per-variant; template allowlist sync may change variant defaults), `products.barcode_added|_removed` (no price effect — lookup alias only), `products.reorder_rule_created|_updated|_disabled` (none — no-op guard), `products.brand_created|_updated` (none — no-op guard), `masters.unit_of_measure_created|_updated|_retired` (UOM validation/conversion-factor invalidation; products itself consumes only these three — `default_set`/`removed` exist on masters but are out of scope), `masters.contact_created|_updated` (party-specific defaults). NOT consumed (do not implement): `inventory.batch_created|_expired` and `inventory.stock_changed` as pricelist inputs — the topics do not exist (inventory stub); batch gating derives from `products_item.has_batch_no` and stock-valuation reads stay a future pull interface.

## 7. Proposed shape (Aspen OS conventions)

- `$name = "pricelist"`, `$dependencies = ["products"]`, `$consumes = [products.item_created|_updated|_disabled|_archived, products.item_group_created|_updated|_disabled, products.variant_created|_template_updated, products.barcode_added|_removed, products.reorder_rule_created|_updated|_disabled, products.brand_created|_updated, masters.unit_of_measure_created|_updated|_retired, masters.contact_created|_updated]`, units `db`, `pubsub` (+ `audit` from context). Stateless (no cron; expiry derived on read + explicit `expireDuePrices` action callable from host scheduler).
- Workflow groups (one action per file under `workflows/<entity>/<verb>.ts`, mirroring products `Workflow.name("products.<group>.<verb>")` + `ctx.step.run("query"|"audit-and-notify")` + `ctx.audit.write` + `ctx.pubsub.publish` patterns): `p.pricelist.lists` (create/get/list/update/disable/delete — delete blocked while rows exist, mirroring products `delete` guards), `p.pricelist.itemPrices` (create/get/list/update/expire/assign-to-parties + `hasPriceReferences`), `p.pricelist.fetch` (query-only: `getRate`, `getRatesForList`, `getActiveForItem` — each starting with the §3.0 eligibility pre-check), `p.pricelist.settings` (singleton get/update with get-auto-creates semantics copied from `products.settings.get`).
- Tables (all tenant, `snake_case`, `id: uuidv7().primaryKey()`, `timestamptz`, `numeric()` rates, no FKs, alphabetical columns): `pricelist_list`, `pricelist_item_price`, `pricelist_setting` (singleton). Enums (`pricelist_*` pgEnums, lowercase values): `applicability` (`selling|buying|both`), `doc_status`.
- Validation: Valibot `Create<Entity>Schema / Update<Entity>Schema / <Entity>FiltersSchema` (validity overlap check in handler via `parse` + range query); `Workflow.input(schema)` + `parse` for narrowed checks; `stripUndefined()` on updates; `?? null` DB writes / `?? undefined` event payloads; DB-boundary camelCase→snake_case mapping.
- ACL (`src/auth.ts` via `defineAcl`, mirroring products `auth.ts` shape): `list` (create/read/update/disable/delete), `item_price` (create/read/update/expire), `fetch` (read-only), `setting` (read/update).
- Indexes: `idx_<table>_<column>`; FK-less soft-FK indexes on `item_id`, `price_list_id`, `customer_id`, `supplier_id`, `batch_no`, `valid_from`, `valid_upto`; composite uniqueness enforced in handler (no DB exclusion constraint in v1).

## 9. Phasing

- **MVP (this spec):** §§3–7 as above, selling/buying/both lists, UOM-specific + `price_not_uom_dependent` scaling (masters category-checked, `must_be_whole_number`-aware), min-qty/packing-unit (floor: products `minimum_order_qty`), party/batch specificity (batch = `has_batch_no`-gated label; inventory stub), validity windows, row-level lead-time differentiation (vs item-level `products_item.lead_time_days`), auto-insert-on-first-use (products flag read-only + `mark-transacted` semantics + buying-side `last_purchase_rate` via `products.item.update`), deterministic fetch order (eligibility → specificity → validity → min-qty → lead-time) with `resolve-defaults` group fallback.
- **Phase 2 (deferred, not in MVP):** Pricing-rule engine, tiered/slab pricing, currency conversion, bulk import shooting, price-approval workflows, POS price sync, promotion calendars, live inventory-batch validation and `basic_rate` valuation pull (blocked on inventory stub growing topics/tables). Each needs its own ADR/spec — do not smuggle into MVP.

## 10. Open questions

1. Validity overlap: DB exclusion constraint vs handler-level range check (recommendation: handler check in v1, matching products' handler-enforced uniqueness e.g. `assertItemCodeUnique`/UOM-duplicate guards — constraint later)?
2. `price_not_uom_dependent` default: per-list flag defaulting false (recommendation: yes, ERPNext parity) or tenant-wide default?
3. Auto-insert writer: keep flag in products settings with pricelist as executor (recommendation: yes — RESOLVED by implementation: `products.settings.update` is sole writer, `products.settings.get` auto-creates; pricelist reads only)?
4. `packing_unit` semantics: keep ERPNext multiplier behavior (recommendation: yes, with `0/NULL = no-op` guard)?
5. Expiry job: on-read derivation + explicit `expireDuePrices` (recommendation: yes, no dedicated cron in v1 — matches products' stateless/no-cron posture) vs `pricelist.expiry-scan` cron?
6. Price List rename: backfill `products_item.default_price_list` + `products_item_group.default_price_list` text labels on rename (they store labels, not ids), or freeze list `name` as immutable and add a separate display label?
7. Item delete coordination: `products.item.delete` cannot see pricelist rows (no FKs) — host must call pricelist `hasPriceReferences` before delete, or accept orphan rows keyed by deleted `item_id`?

## 11. Implementation (in `@aspen-os/products`, not a separate package)

Implemented inside `packages/products` (`$name = "products"`) per host decision — a module cannot depend on itself, so the §7 `$dependencies = ["products"]` is vacuous here and same-module reads replace the cross-module calls. Deliberate deviations from §§3–7:

1. Table names are `products_`-prefixed (`products_price_list`, `products_item_price`, `products_pricelist_setting`), not `pricelist_`-prefixed.
2. Event topics are `products.price_list_created|_updated|_disabled` and `products.item_price_created|_updated|_expired` (constants `PRICE_LIST_EVENTS`, `ITEM_PRICE_EVENTS`), not `pricelist.*`. No `$consumes` change was needed (same module).
3. No `inventory.batch_*` consumption (topics do not exist); `batch_no` is a label gated on `products_item.has_batch_no`.
4. `valid_from`/`valid_upto` use `date()` columns (repo date-only convention), not `timestamptz`.
5. `getRate` increments `fetch_count`/`last_fetched_at` on the winning row — the single fetch-path write besides auto-insert — required to enforce "cancelled only before first fetch-use" and "never hard-delete used rows".
6. Same-module direct writes replace cross-module calls: auto-insert sets `products_item.has_transactions` and buying-side `last_purchase_rate` via direct updates (same transaction as the price insert), and group-default fallback re-implements the `resolve-defaults` ancestor walk in `services/price-fetch-service.ts` (`resolvePriceListLabel`) instead of invoking the `products.lookup.resolve-defaults` workflow.
7. `assign_to_parties` is all-or-nothing sequential (throws on first conflict); `min_qty` below item `minimum_order_qty` is permitted (the spec's "warn" has no channel — callers surface `minimum_order_qty` alongside the rate).
8. Workflow groups: `priceLists`, `itemPrices`, `priceFetch`, `pricelistSettings`; ACL resources `price_list`, `item_price`, `price_fetch` (read-only), `pricelist_setting`; audit entities `products:price-list`, `products:item-price`, `products:pricelist-setting` with added `cancelled`/`expired` audit actions.
